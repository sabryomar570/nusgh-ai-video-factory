# NUSGH MVP — تدقيق القالب وقيود التشغيل

## النتيجة التنفيذية

يوفر القالب الحالي أساسًا مناسبًا لمنظومة NUSGH: واجهة React، وخلفية Express مع tRPC، وقاعدة MySQL عبر Drizzle، ومصادقة Manus، وتخزين S3، وHeartbeat للمهام المجدولة. تم إنشاء مخطط البيانات الأساسي وربطه بترحيل قاعدة البيانات، كما أضيفت طبقة أولية للطوابير والمزودين مع اختبارات وحدة.

> لا يعني هذا أن كل قدرة إنتاج فيديو متاحة الآن. يلتزم المشروع بوسم أي خدمة غير موصولة أو غير قابلة للتشغيل بميزانية $0 بوضوح، بدل محاكاتها كأنها اتصال إنتاجي.

| المجال | ما يدعمه القالب الآن | القرار في NUSGH |
|---|---|---|
| الواجهة الداخلية | React وTailwind ومكوّن Sidebar جاهز | بناء لوحة تحكم مظلمة عربية متجاوبة فوق المكوّن الجاهز بدل إعادة اختراع هيكل التنقل. |
| منطق الخلفية | Express وtRPC وإجراءات محمية | كل العمليات الإدارية وخط الإنتاج تمر عبر tRPC مع صلاحيات Admin/Owner. |
| البيانات | MySQL وDrizzle وترحيلات | تخزين حالة خط الإنتاج، مراجعاته، الأصول، الوظائف، التحليلات وسجل التدقيق. |
| الملفات | S3 مدمج | تخزين مراجع الأصول والرندر والصوت والـthumbnail، لا تخزين bytes داخل قاعدة البيانات. |
| الجدولة | Heartbeat ومسارات `/api/scheduled/*` | لا `setInterval` أو `node-cron` داخل العملية. أي جدولة مستقبلية تكون idempotent ومبنية على `taskUid`. |
| المصادقة | Manus OAuth | الواجهة الإدارية تتطلب الدخول، بينما تحكم Telegram يستخدم Allowlist منفصلًا لمعرف المستخدم. |

## القيود التي تحكم المعمارية

تعمل الاستضافة الافتراضية في نمط Autoscale بعملية Node واحدة ذات دورة حياة مرتبطة بالطلب. لذلك لا يجوز افتراض وجود worker دائم في الذاكرة، أو عملية رندر طويلة، أو مؤقت داخل التطبيق. كل عمل متكرر أو مؤجل سيتحول إلى Heartbeat عبر endpoint مخصص بعد النشر، مع إعادة محاولة آمنة وحماية من التكرار.

تحت قيد الإطلاق البالغ $0 وعدم وجود جهاز شخصي أو GPU دائم، لا يُعد الرندر الثقيل أو تحويل الفيديو طويل المدة قدرة إنتاجية مضمونة داخل الخادم. طبقة المزودين تحفظ هذا الحد بوضوح: يمكن إكمال التخطيط وطلب المزود وتخزين النتيجة عندما تتوفر خدمة متوافقة، لكن أي مزود غير موصول أو غير قابل للتشغيل يوضع في حالة `unconfigured` أو `unavailable`، ولا يدّعي النظام نجاح الرندر أو النشر.

## قرارات الأمان والحوكمة

المراجعة البشرية هي الوضع الافتراضي. لا يمكن لمسار `conditional_auto` تجاوز حالات فشل السلامة أو التحقق من الادعاء أو غموض حقوق الأصل أو فشل المزود أو الرندر أو الجودة. تحفظ الوظائف هذه الحالات بوضع `requires_review`، وتحفظ الأحداث في سجل التدقيق.

لا يتم حفظ مفاتيح Telegram أو YouTube أو مزودي الإنتاج داخل الجداول أو السجلات. تستخدم الأسرار متغيرات البيئة فقط، بينما تحفظ قاعدة البيانات اسم مرجع سرّي أو حالة اتصال غير حساسة. ربط YouTube اللاحق يجب أن يقتصر على OAuth 2.0 الرسمي، ولا يتضمن كلمات مرور أو cookies أو أتمتة تسجيل دخول.

## ما يتطلب أسرارًا أو نشرًا لاحقًا

| القدرة | متطلب خارجي | حالة البناء قبل توفيره |
|---|---|---|
| Telegram Control Center | `TELEGRAM_BOT_TOKEN` ومعرف المالك | يمكن بناء الواجهة ومنطق الرسائل؛ لا يتم استقبال أو إرسال رسائل فعلية قبل توفير السر. |
| YouTube Publish & Analytics | بيانات اعتماد OAuth الرسمية واعتماد المستخدم | يمكن بناء adapter والحواجز؛ تبقى الحالة `unconfigured`. |
| TTS / صور / رندر | مزود متوافق ورخصة/حصة مؤكدة | يعمل abstraction والـqueue؛ التنفيذ الفعلي موسوم حسب حالة المزود. |
| Daily Autopilot | نشر التطبيق ثم Heartbeat مع إعداد schedule | لا تنشأ مهمة دورية قبل نشر نسخة فيها endpoint مخصص. |

## ملاحظة موصل Telegram

سيستخدم مركز التحكم Webhook رسميًا عبر `setWebhook`، وليس polling داخل عملية دائمة. سيُفحص ترويسة `X-Telegram-Bot-Api-Secret-Token` قبل معالجة كل تحديث، ثم يُفحص `from.id` مقابل قائمة السماح الخاصة بالمالك. هذا يتطلب نشر التطبيق ونقطة HTTPS عامة قبل تفعيل Webhook، إلى جانب `TELEGRAM_BOT_TOKEN` وسر Webhook مستقل. المصدر: [Telegram Bot API](https://core.telegram.org/bots/api#setwebhook).

## المراحل التالية

سيبدأ التطوير بالواجهة الداخلية التي تعرض حالة حقيقية من قاعدة البيانات، ثم مركز الموافقة والتحكم، ثم تتوسع موصلات الإنتاج بالتتابع. يجب أن تبقى شاشة المزودين مصدر الحقيقة لحالة كل اتصال، وتظهر الحدود والتوقفات بدل أزرار شكلية غير مرتبطة بخلفية حقيقية.
